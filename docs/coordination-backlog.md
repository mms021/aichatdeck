# Доработки подключения и координации

## Канонические задачи (23 сентября 2026)

Использовать подробные задачи, не создавать повторные A–E:

| Направление | task_id |
| --- | --- |
| A | task-14840bcd-5915-4f7d-b77b-e73cc7ea2964 |
| B | task-8e00b0ec-9d3b-4d7f-abbb-0e80a69bb330 |
| C | task-88697312-8b02-40d1-b41b-ec8118c2537c |
| D | task-d980079d-0e2d-43bb-8f80-dd7823ab1d6c |
| E | task-ca28d93a-ed21-40d5-b606-3575b0691bc4 |
| MCP | task-c0fc518f-eebc-4a0b-9349-f03fc792c010 |

Отмена свободной задачи: `POST /tasks/{task_id}/cancel`, тело
`{"reason":"Duplicate of task-..."}`. Только создатель, только OPEN без
исполнителя; повторная отмена идемпотентна. Статус CANCELLED, причина,
автор и время отмены сохраняются в context.cancellation. История не удаляется.
Отменённую задачу нельзя взять в работу. Занятая задача возвращает 409.

Цель: несколько агентов работают в одном проекте через одну базу, сохраняя
личность после выхода и перезапуска. Обычный выход сейчас не отзывает токен:
наблюдавшиеся 403 были связаны с другой базой.

## A. Идентичность сервера и диагностика credentials

Исполнитель: backend developer.
Сохранить случайный instance_id в БД, возвращать его в manifest и записывать
в state агента. При несовпадении сообщать wrong_instance, сохраняя исходный
state. После рестарта с той же базой ID неизменен; другая база получает другой
ID. Перенос той же базы в Docker сохраняет ID. Не раскрывать токены, хеши,
пути БД и существование чужих credentials в публичных ответах.

## B. Надёжное подключение и хранение state

Исполнитель: CLI developer. Зависит от A.
Повторное подключение, выход, потеря связи и перезапуск сервера сохраняют
agent_id. Credentials хранятся атомарно с правами 600 вне Git, отдельно по
instance_id и личности агента. Конкурентные подключения не перезаписывают
state. При повреждённом state нет автоматической новой регистрации. При 403
нет переключения на worker-2 или другую личность. Явный отзыв остаётся рабочим.
Не печатать токены в вывод, команды и журналы.

## C. Один запуск сервера и переносимость

Исполнитель: backend developer.
Зафиксировать единый способ запуска с явным адресом и SQLite-путём относительно
каталога запуска; не создавать скрытую вторую базу при подключении агента.
Добавить понятную диагностику занятого порта. Описать Docker volume и перенос
базы без потери credentials, проектов и checkpoint. Старые базы не удалять.

## D. Изоляция и продолжение задач

Исполнитель: coordination developer.
Привязать выполнение задачи к отдельному worktree, ветке и базовому коммиту.
Checkpoint содержит результат, следующие шаги и ссылки на изменения. После
смены оркестратора продолжать активные задачи без дублей. Предусмотреть передачу
проверки при недоступном создателе с явными полномочиями и запретом самопроверки.
Не выполнять автоматический merge или push без соответствующего поручения.

## E. Приёмочные проверки

Исполнитель: tester, отличный от автора проверяемых изменений. Зависит от A–D.
Проверить: restart агента/MCP/сервера, перенос той же БД, подмена БД, два
одновременных подключения, отозванный credential, отсутствие утечек секретов,
смена оркестратора и запрет старого generation, сохранение checkpoint,
раздельные роли в двух проектах, независимые worktree.

Для каждого задания указать allowed_work_roles и критерии готовности.
Каждый исполнитель сохраняет checkpoint перед передачей; отчёт без реально
выполненных проверок не считать подтверждением успеха.
